# TransMixer：两个模态怎么交流的对照实验

这批实验研究的是：在你已有的固定1:1 TransMixer上，HSI与LiDAR/SAR在最终融合之前交换信息，是否比直接拼接更有用，以及应当怎样交换。代码已实现7组；本机实际数据实验使用Houston2013的HSI＋LiDAR。SAR接口通过了4通道合成输入的前向、反向检查，尚无真实SAR数据结果。

## 先读懂每一组在问什么

“A→B”表示A提供信息，B更新特征；不表示只训练B。各组仍然通过同一个分类损失联合训练，不包含教师模型或蒸馏损失。

| 组别 | 人话解释 | 用来回答的问题 |
|---|---|---|
| F0 原始拼接 | 两个人分别做题，最后把答案放在一起交给分类器 | 没有额外交互时的基准 |
| F1 辅助自增强 | LiDAR先自己再想一遍，不看HSI | 提升会不会仅仅来自多加了一层，而不是交流 |
| F2 LiDAR→HSI | HSI做判断时，去LiDAR那里查询辅助信息 | 高度/结构信息能否帮助光谱分支 |
| F3 HSI→LiDAR | LiDAR做判断时，去HSI那里查询辅助信息 | 光谱语义能否补足较浅的辅助分支 |
| F4 整体双向 | 双方都查询对方，并各自更新 | 双向是否比单向值得 |
| F5 按分工双向 | HSI全局流做跨位置查询，局部流在附近交换信息 | 交流方式是否应该配合原来的全局/局部分工 |
| F6 交换分工 | 把F5的两种交流方式调换 | F5如果有效，是分工匹配有效，还是随便加模块都有效 |

F1–F4使用相同结构的注意力消息模块。双向组共享两方向的消息模块参数，但会调用两次，因此计算量更高。F5与F6参数量、初始权重完全一致，仅改变算子分配；这对比较比“复杂模型超过简单模型”更能说明分工的作用。

F1只是辅助分支自增强的容量对照，不能排除所有“增加容量”的解释。如果后续F4收益明显，仍可补HSI自增强、双分支各自自增强等更严格对照。

## 具体放在哪里

原HSI分支：前端卷积 → TransMixer块1 → 块2中的SSM → 分成全局流与局部流 → 各自处理 → 合并投影和残差。

本批交互接在块2的两条流各自处理之后、合并投影之前。LiDAR/SAR仍由原来的浅卷积提取特征，再参与交互。最后仍使用原来的双模态拼接、1×1卷积、池化与分类器。F0直接调用原模型前向。

F5不是把已经融合的HSI通道随便切成两半，而是使用原模型真正的全局流和局部流。辅助模态的两组通道由可学习投影产生，不能称为天然的“全局特征”和“局部特征”。

## 交流动作是什么

交叉注意力：目标分支提出查询，从来源分支的各位置提取加权信息。原有位置坐标对齐，但注意力可以在整个11×11图块内寻找信息。

局部交互：来源特征经过3×3深度卷积，目标与来源共同决定门控权重，只向目标传入附近的信息。

每条消息都按 `新特征 = 旧特征 + gamma × 消息` 更新。可学习的 `gamma` 从0开始，所以初始预测与原始模型一致。训练先决定要不要接收消息，再逐渐学习消息内容。双向更新都读取更新前的特征，避免先更新的一方占据额外优势。

这里的 `gamma` 是可以为正、也可以为负的残差系数，绝对值不能直接解释成某个模态的贡献百分比。短程训练中它可能还很小，因此10轮结果对慢热方法不构成否定。

## 怎样保证比较相对公平

- 每组使用相同主干、隐藏维64、2个块、PCA30、11×11窗口、批大小128、AdamW、学习率0.0001、权重衰减0.01。
- 同一训练种子的原有参数逐项一致；新增模块初始化不消耗后续训练的外部随机数。相同种子的数据顺序和配对翻转一致。
- 从官方2832个训练中心按类别分层划出约20%作为固定验证集；所有组及后续训练种子共享这个划分。具体数量见输出的data_manifest.json。
- 每轮只看验证集，用验证OA选最佳权重；OA相同则选择验证损失更低的权重。初筛不计算测试集成绩。
- 所有组统一使用严格确定性计算，SDP数学后端，关闭TF32及Flash/内存优化SDP。首次试跑的非确定性警告已通过重新跑整批处理。
- 保存配置、数据哈希、划分索引、源代码哈希、每轮日志、最佳权重、验证预测、逐类指标、参数量、显存和模型前向时延。

注意：PCA和标准化仍利用全图无标签像素，是传导式预处理。训练、验证、测试的中心互不相交，但相邻图块可能重叠。这是同场景实验，不能据此声称对全新地区具有同样效果。

旧B1–B4报告与本批的训练样本数、选模协议不同，不能把旧测试OA和新验证OA放在同一张排名表里。

## 怎样运行

在仓库根目录的终端执行，或者在VS Code打开入口脚本直接运行。默认是7组、seed6、每组10轮的初筛，保存到新的时间戳目录。

```powershell
python scripts/train_transmixer_fusion.py
```

先检查计划，不启动训练：

```powershell
python scripts/train_transmixer_fusion.py --dry-run
```

正式确认配置是全部7组、每组100轮、训练种子6/7/8。仍按固定验证集选权重，选好后评估该权重的官方测试集一次：

```powershell
python scripts/train_transmixer_fusion.py --config configs/fusion_confirm.json
```

只跑某一对比较，例如分工与交换分工：

```powershell
python scripts/train_transmixer_fusion.py --config configs/fusion_confirm.json --variants F0 F5 F6
```

先定下候选与训练预算，再开始正式训练；不要根据测试成绩反复选模块。选择性只跑某对比较时，也要报告筛选过程。

为Berlin准备好相应数据文件后可使用 `--datasets Berlin`。缺文件会在训练前报错；目前本机没有该数据。模型默认支持当前Berlin配置对应的4通道辅助输入，真实通道和配准仍应以实际数据核对。

指定输出名可以加 `--run-tag 名称`，仅支持英文字母、数字、下划线与短横线，已有目录会拒绝覆盖。GPU不可用时会报错，需明确传 `--device cpu` 才使用CPU。

## 如何根据结果决定下一步

1. F1已经超过F0、F4又与F1差不多：首先考虑辅助分支能力不足，不宜把收益全归功于跨模态交流。
2. F2比F3好：优先确认“辅助指导HSI”；反过来则优先确认“HSI指导辅助”。需多个种子支持。
3. F4持续超过F1、F2、F3：双向交互值得继续，但仍需计入时延、参数和更完整自增强对照。
4. F5持续超过F6：分工匹配值得研究。F5只超过F4不足以证明这一点，因为两者结构和参数不同。
5. 各组接近：先检查训练是否充分、消息强度是否学起来；不要立即叠加蒸馏、超图等新模块。

10轮、单种子仅用于确认能训练、观察早期趋势。所有结论都要等相同预算的完整训练与多种子对照。验证集约数百个中心，一个样本就可能改变约0.18个百分点；小幅差距尤其需要谨慎。

新增模型在 `src/models/transmixer_fusion/`，独立实验引擎是 `src/fusion_experiment.py`。该融合批次未修改原模型和旧训练器；后续蒸馏批次在旧训练器中增加了可选损失与诊断回调，默认仍使用原 CE。本批请使用专用脚本以确保验证选模，普通旧训练入口不自动获得新协议。完整结果与后续原流程、蒸馏对照见 [周末研究归档](results/weekend_20261024_25/README.md)。

```powershell
$env:CUBLAS_WORKSPACE_CONFIG=':4096:8'
python -m unittest src.models.transmixer_fusion.test_fusion src.models.transmixer_fusion.test_protocol src.models.transmixer_distill.test_distillation src.models.transmixer_ablation.test_feature_ablation -v
```
